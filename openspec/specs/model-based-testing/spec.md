# model-based-testing Specification

## Purpose
Defines how rind-ui derives tests from each component's machine graph and contract:
every state and transition is exercised in every declared modality, the real
component is compared against the pure machine after each step, and generic and
per-component invariants are checked — for rind-ui itself and for consumers'
own wrappers.
## Requirements
### Requirement: Graph Extraction

`@rind-ui/testing` SHALL extract from a machine definition, without running it, a
graph of states (with tags, entry, exit and effects) and edges (source, target,
event, guard, actions), including delayed edges, controllable `$sync` edges and
prop-change edges.

#### Scenario: Delayed and controlled edges

- **WHEN** a machine declares an `after` transition and a controllable bound to
  states
- **THEN** the graph contains an `after:<delay>` edge and `$sync:<value>` edges

### Requirement: Path Generation

Paths SHALL be generated by shortest-path search for two coverage levels: every
state, and every transition (the default). Paths that are prefixes of other paths
SHALL be dropped. Events with no mapping in the contract SHALL be reported as
uncovered in a single explicit test result, never skipped silently.

#### Scenario: Transition coverage

- **WHEN** paths are generated with transition coverage
- **THEN** every edge of the graph appears in at least one path, or is listed as
  uncovered

### Requirement: The Runner

`testMachine` SHALL register one test per path and modality through a test function
the caller passes in (so it depends on no test runner), named after the path. Each
test SHALL render a fresh component, run each step's mapped action through the
driver, advance a headless copy of the machine (the oracle) with the same props,
assert that the contract's state observations for the oracle's state hold, and
check every applicable invariant. A failure SHALL report the path up to the failing
step so it can be replayed.

#### Scenario: Guard decides the expected state

- **WHEN** a path presses Escape on a component whose props disable closing on
  Escape
- **THEN** the oracle stays in `open` and the runner asserts the component is still
  open

#### Scenario: Readable failure

- **WHEN** a step fails
- **THEN** the report shows the modality, the path so far and the failing
  observation

### Requirement: Generic Invariants

The runner SHALL check, after every step and with no per-component code (rule
numbers refer to the checklist in `docs/research/accessibility.md`):

- observations match the oracle's state; every part for which the contract declares
  a `data-state` (per part, for the oracle's state) carries exactly that value; item
  parts are checked against the state the contract declares for each item (for
  example `active`/`inactive` tabs), never skipped;
- exactly one element matches the anchor; no uncaught error or `console.error`
  occurred;
- every element whose role requires a name has a non-empty accessible name (1);
  when a visible Label or Title part is rendered, the accessible name contains its
  text (5);
- every IDREF (`aria-labelledby`, `aria-describedby`, `aria-controls`,
  `aria-activedescendant`, `aria-owns`, `aria-details`, `for`) resolves to an element
  in the same document or root (2); every id the component renders is unique (3);
- `aria-expanded`, `aria-selected`, `aria-checked`, `aria-pressed`, `aria-disabled`
  and `aria-invalid` match the machine state, and the matching `data-*` attribute
  agrees (6);
- the focused element is never inside `aria-hidden="true"` or `inert`, and no
  focusable element is inside `aria-hidden="true"` (10);
- if focus was inside the component before the step, it is inside the component or
  on its documented restore target afterwards — never on `body` (11);
- the component renders no `aria-live` region of its own unless its contract
  declares the `live-region` trait (23);
- every `aria-labelledby` / `aria-describedby` target of an exposed element is
  outside any `inert` subtree (name sources stay reachable);
- neither `<html>` nor `<body>` carries `aria-hidden` or `inert`, and every
  attribute or style the component added outside its own parts is removed once it
  has closed;
- an element's accessible name and accessible description are not identical (no
  double reading).

Assistive-technology research behind these checks:
`docs/research/assistive-tech-and-a11y-testing.md` §2.10.

Depending on the contract's traits it SHALL also check:

- `disclosure`: the trigger's `aria-expanded` mirrors open state; content is absent,
  `hidden`, or (with `hiddenUntilFound`) mounted with `hidden="until-found"` once
  closed (30);
- `layer`: Escape closes only the topmost layer and is a no-op with nothing open
  (19); focus is never on `body` while a layer is open;
- `restores-focus`: after closing, focus is on the trigger (when connected and not
  inert) or the declared final-focus part (13);
- `composite-roving`: exactly one item has `tabIndex=0` (8);
- `composite-activedescendant`: only the input or container is tabbable, and
  `aria-activedescendant` is empty or points at a rendered element inside the
  controlled popup carrying `data-highlighted` (8, 9);
- `selectable`: every selectable item has `aria-selected` (or `aria-checked`) set
  explicitly to `"true"` or `"false"`, single selection has at most one `"true"`, and
  the true set equals the machine's selected set, not the highlight;
- `set-metadata`: `aria-posinset` is within `[1, aria-setsize]`, unique within its set
  and equal to the visible order after filtering;
- `valued`: `aria-valuenow` / `aria-valuetext` and the value text equal the machine's
  value in the same step;
- `live-region`: every live region the component renders exists before its first
  message and is never inside an `aria-hidden` or `inert` subtree;
- `timed`: auto-dismiss or auto-advance timers do not elapse while the component is
  hovered, focused or the document is hidden (27).

#### Scenario: Dangling relation

- **WHEN** a part's `aria-controls` references an id that is not in the document
- **THEN** the step fails naming the attribute and the missing id

#### Scenario: Focus lost

- **WHEN** a layer is open and focus lands on `body` after a step
- **THEN** the step fails

#### Scenario: Unnamed control

- **WHEN** a button part renders with no accessible name
- **THEN** the step fails naming the part

### Requirement: Virtual Modality Runs

The runner SHALL include the `virtual` modality in the default set of modalities for
every action that has a pointer implementation, so every transition reachable by
pointer is also exercised the way a screen reader activates it.

#### Scenario: Pointer-only trigger handling

- **WHEN** a component opens on `pointerdown` but not on a bare `click`
- **THEN** the virtual-modality path for `OPEN` fails

### Requirement: Right-To-Left Runs

The runner SHALL be able to run every path a second time with the component
rendered under `dir="rtl"`, mapping horizontal arrow-key actions to their mirrored
logical events, so the same oracle expectations hold (17). Contracts that declare
the `directional` trait SHALL be run in both directions by default.

#### Scenario: Mirrored arrows

- **WHEN** a `directional` component is run under `dir="rtl"`
- **THEN** pressing ArrowLeft produces the event ArrowRight produces under `ltr`, and
  vertical arrows, Home, End, PageUp and PageDown are unchanged

### Requirement: Prop Steps

`testMachine` SHALL accept a function that re-renders the component with new props,
and contracts SHALL be able to map `$sync:<value>` and `$props:<prop>` edges to prop
steps (the props to apply). A mapped prop step SHALL re-render through that function,
feed the same props to the oracle, and be checked like any other step. Edges whose
prop step is not mapped SHALL be reported as uncovered.

#### Scenario: Controlled open from the parent

- **WHEN** a path contains the edge `closed —$sync:open→ open` and the contract maps it
  to `{ open: true }`
- **THEN** the runner re-renders with `open: true`, the oracle takes the `$sync` edge,
  and the component's observations must match `open`

### Requirement: Per-Component And Consumer Invariants

A contract SHALL be able to ship invariants of its own, which are always on for that
contract. A consumer SHALL be able to add invariants and SHALL NOT be able to turn
off generic or per-component ones.

#### Scenario: Consumer wrapper

- **WHEN** a consumer runs `testMachine` on their styled wrapper and the wrapper
  removes a required ARIA attribute
- **THEN** the corresponding invariant fails

### Requirement: Accessibility Check Per State

The runner SHALL accept an accessibility checker (for example axe) and run it once
per distinct state reached in a test, failing the step on violations.

#### Scenario: Violation in the open state

- **WHEN** the open state renders a part with no accessible name
- **THEN** the step that reached `open` fails with the checker's report

### Requirement: Valued Trait Expectations

For contracts with the `valued` trait, the runner SHALL take the expected values from the
contract when it declares them (`valued: { values(view, props), valueText?(view, index, props) }`,
`props` being the oracle's props) and otherwise from the machine's `value`. The expected
values SHALL be a list, matched in DOM order to the elements that carry `aria-valuenow` or
represent a valued role (`slider`, `progressbar`, `meter`, `spinbutton`) and are not hidden
from assistive technology, so multi-thumb components are checked thumb by thumb. A `null`
entry SHALL require that element to have no `aria-valuenow`, and no `aria-valuetext` unless
the contract declares `valueText` for it (an empty Number Input says "Empty"). When the
contract declares `valueText`, each element's `aria-valuetext` SHALL equal it; otherwise a
numeric-looking value text SHALL be compared with the value only when it is the plain
`String(value)` form, so locale grouping such as "1.200" is never misread as 1.2.

#### Scenario: Multi-thumb mismatch

- **WHEN** a two-thumb slider's oracle values are `[20, 80]` and the second thumb has
  `aria-valuenow="79"`
- **THEN** the step fails naming the second thumb

#### Scenario: Indeterminate progress

- **WHEN** a progress oracle value is `null` and the root still carries `aria-valuenow`
- **THEN** the step fails naming the attribute

#### Scenario: Locale grouping

- **WHEN** a German-locale component shows `aria-valuetext="1.200"` for the value 1200
  and the contract declares no `valueText`
- **THEN** the step passes

#### Scenario: Empty number input

- **WHEN** a Number Input's oracle value is `null`, its input has no `aria-valuenow` and
  `aria-valuetext="Empty"`, and the contract declares `valueText` returning "Empty"
- **THEN** the step passes
